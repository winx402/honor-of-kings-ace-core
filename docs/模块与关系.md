# 模块与关系定义

定义版本：0.2.0；状态：已定义、未实现。游戏研究依据见[游戏理解与依据](游戏理解与依据.md)。

这里的模块是仓库中的内容责任边界，不是已实现的软件包、数据库表或服务。沿用现有 `rules/`、`entities/`、`relations/` 等目录，不引入网站模块。内部英文标识是本项目命名，不冒充官方接口或游戏资源 ID。

## 必须分开的对象

| 概念 | 保存什么 | 不应混同 |
| --- | --- | --- |
| 英雄定义 | 身份、品阶、阵营、属性、效果与技能引用 | 手里的一张牌、某局具体单位 |
| 卡牌定义/实例 | 载体指向、使用方式；具体牌的所有者、变体与有效期 | 使用后持续存在的天赋或装备 |
| 局内英雄成长状态 | 永久/临时等级、觉醒进度/状态与技能强化 | 棋手等级、固定品阶 |
| 参战单位 | 当前生命/法力、位置、目标、状态与来源 | 仅仅英雄；还可能是图腾、召唤物、棋手衍生单位 |
| 棋手定义/参与者状态 | 技能与任务定义；局内生命、等级、资源、牌和选择 | 用户账号、局外好感度 |
| 能力/效果/关键词/状态 | 能力组合、动作语义、触发约定、局内持续变化 | 一张混合“buff”标签表 |
| 版本记录/内容身份 | 稳定实体身份及某范围下的修订 | 文件更新时间、统一“最新版” |

英雄是一类单位定义，但并非所有单位都是英雄。天赋可生成天赋牌，装备可由装备载体产生，棋手任务可生成秘技牌；这些关系不能按同名记录自动合并。

## 模块依赖

下图是简化依赖图，箭头表示“后者使用前者的契约”，不是触发顺序。完整清单以 modules.json 的 `depends_on` 为准，字段方向为“本模块依赖列出的模块”。

```mermaid
flowchart TD
  V[公共标识与词汇] --> P[来源与证据]
  P --> R[版本与范围]
  R --> M[关键词 事件 效果]
  M --> H[英雄 卡牌 棋手 装备 天赋定义]
  M --> G[对局与回合]
  G --> E[能量 商店 拍卖]
  H --> C[战斗与特殊单位]
  G --> C
  E --> O[模式与规则变体]
  C --> O
  O --> S[阵容与打法]
  H --> S
  S --> Q
  R --> L[对象关系索引]
  P --> L
  H --> Q[验证与覆盖率]
  O --> Q
  L --> Q
```

来源与适用范围是每条内容、公式和关系的共用要求，图中没有画出所有重复箭头。模式层引用明确基线与覆盖项，不复制一整套同名实体。对象之间可能存在循环引用或触发链，这不表示模块依赖也应形成循环。

## 游戏对象关系

对象关系分为身份关联、机制语义与可用性、实例归属、适用范围、证据、策略建议六类。关系目录中的60种类型是表达能力定义，并非60条已确认游戏规则；允许多对多也不是宣称游戏无数量上限。

```mermaid
flowchart LR
  CP[棋手定义] -->|具有| TASK[秘技任务]
  TASK -->|奖励| CARD[卡牌定义]
  CP -->|专属| TALENT[天赋定义]
  HC[英雄牌定义] -->|指向| HERO[英雄定义]
  HERO -->|归属| FACTION[阵营]
  HERO -->|觉醒变体和等级强化| VARIANT[成长规则]
  HERO -->|引用| ABILITY[能力]
  TALENT -->|引用| ABILITY
  EQUIP[装备定义] -->|引用| ABILITY
  CP -->|引用| ABILITY
  CARD -->|引用| ABILITY
  ABILITY -->|包含| EFFECT[效果]
  EFFECT -->|监听| EVENT[事件]
  EFFECT -->|条件和目标| SELECTOR[条件 目标选择 公式]
  EFFECT -->|生成| CARD
  EFFECT -->|召唤| UNIT[特殊单位定义]
  EFFECT -->|赋予| EQUIP
```

实例关系必须归属于明确快照或等价不可变观察上下文；坐标通过 `relation_attributes.position` 或 `position_ref` 表达，装备槽位可用 `slot_ref`。观察时间不自动证明状态在两个快照之间持续有效，同一实例在不同快照的关系不构成冲突。

本图刻意只表达定义关系。某局中谁持有哪张牌、谁穿戴装备、战斗单位的复制来源和所在格子，是带时间和实例标识的关系，不能写回英雄静态定义。

## 效果表达与状态变化

每个效果至少保留：来源能力、事件、条件、目标选择、动作、参数/公式、持续范围、重复/上限、叠加或唯一规则以及验证状态。缺失项写为未知，不补造默认值；复杂能力允许拆成有先后声明的多个效果，未知顺序不能自动排序。

10类关键状态转换已在关系目录中定义：打出英雄牌、觉醒、棋手升级、秘技完成、选择天赋、铸造装备、拍卖结算、开战、单位阵亡、回合结算。它们是需要分别维护前置条件和结果的过程，不是静态图上的普通边。

例如“打出牌 → 合成 → 触发监听 → 生成新牌”是事件链；“棋手 → 秘技任务 → 奖励牌”是内容关联。生成的牌是否自动使用、是否占池、是否继承状态，需要对应范围下的额外规则。

## 版本、证据与未知项契约

后续记录至少遵守这些共同字段，正式序列化 Schema 另行实现：

| 字段组 | 定义 |
| --- | --- |
| 身份 | `entity_id` 稳定且带类型命名空间；名称是显示文本，不能用于唯一关联 |
| 修订 | `revision_id` 指向该实体在明确适用范围下的内容版本；上游 ID 另存映射 |
| 范围 | 游戏规则版本、客户端版本线索、地区/服务器、测试/正式环境、模式和必要的段位/队伍条件；未知显式记录 |
| 内容 | 原始字段、解释后的属性、公式/单位及对应字段主张；不跨版本补齐成“现行”记录 |
| 来源 | `claim_refs` 指向来源和证据；每个关键字段与关系可拥有各自出处 |
| 文字核对 | 未核对、已核对来源、已核对当前游戏文字、存在冲突；不要与实测共用布尔值 |
| 机制核验 | 未实测、结果不确定、有支持观察、有反例；每项关联实验条件与适用范围 |
| 主张类别 | `claim_kind` 区分规则事实、联动主张、策略建议与统计评价，策略成效不由机制验证状态代替 |
| 复用权限 | 原创、明确许可、仅链接、本地研究或未知；未知不自动公开原文/图片 |

规则版本和客户端版本可以不同；公告发布、更新生效、采集时间也分别保存。模式覆盖需定位准确修订，优先级未定义或多个覆盖冲突时保留冲突，不默默采用最后一个文件。

## 定义验收与后续顺序

本次验收：16个模块职责和路径已定义；60种关系类型与10种转换已定义；依赖可解释且无环；覆盖基础规则及用户提出的全部核心内容类别；资料来源、冲突和未验证项可追溯。这里的覆盖仅指类别在定义中有归属，不是游戏数据覆盖率。

后续建议先核对一个包含英雄牌、成长、卡牌效果、战斗技能的样本，再连通棋手任务/衍生牌、装备/特殊单位、天赋/模式。小样本把关系和字段核验通后，再确定正式数据 Schema 和全量采集目录。战斗引擎、自动对局、网站和完整规则发布均未实现。
